# 连接自己的服务器

Dyson Control 在你自己的 Windows 主机上运行。游戏、账号、存档和网络入口由你管理；面板与 Bridge 的本机通信不需要维护者提供的服务。

文档中的 `game.example.com` 和 `control.example.com` 均为占位示例，请替换为自己的地址。

## 两个入口

| 用途 | 连接什么 | 示例 |
| --- | --- | --- |
| 管理员操作面板 | 浏览器通过 HTTP/HTTPS 访问面板 | 本机 `http://127.0.0.1:13020`；远程使用自己的 `https://control.example.com` |
| 玩家加入游戏 | 戴森球计划客户端通过 Nebula 连接游戏 | 自己的主机名或 IP，加上配置的游戏端口，例如 `game.example.com:8469` |

`control.config.json` 中的 `host`、`port` 决定面板监听；`game.address` 是面板展示和分享的游戏地址，填写它不会自动修改 Nebula 端口、防火墙、路由器或 DNS。

## 先在本机或局域网连接

1. 在概览页启动游戏，等待 Bridge 就绪。
2. 给客户端安装与服务器匹配的游戏和模组版本。可以从面板生成 `.r2z`，在 r2modman 中导入并下载对应模组；玩家仍需自行安装正版游戏。
3. 在服务器本机测试时使用 `127.0.0.1`；从另一台局域网设备连接时使用服务器的局域网地址。Nebula 常用游戏端口为 TCP `8469`，以实际 Nebula 配置为准。
4. 如 Windows 防火墙阻止连接，为实际游戏程序或游戏端口添加相应范围的入站规则。客户端通过 Nebula 加入后，确认世界能加载并推进。

另一台设备的 `127.0.0.1` 指向它自己，因此从该设备连接时应使用服务器的地址。

## 需要互联网玩家加入时

- 使用自己可入站的公网地址，将路由器上的游戏 TCP 端口转发到运行 Nebula 的 Windows 主机；云主机还需放行相应安全组与系统防火墙。
- 使用域名时，让自己的 DNS 记录指向游戏入口。动态公网地址可由你自行维护 DDNS。
- 运营商 NAT 等情况无法直接入站时，可以自行选择支持游戏 TCP 连接的转发服务，或让玩家进入你配置的虚拟局域网；对应客户端要求应告知玩家。
- 将最终游戏地址填入 `game.address`，请外部网络的玩家用匹配客户端实际加入。

Nebula 使用 WebSocket（TCP）。选择反向代理或隧道时，需要确认它能转发当前客户端实际使用的游戏连接、握手与认证；管理网页可达不能代替游戏入服测试。

## 远程管理

面板默认保持回环监听，在它前面配置自己的 HTTPS 反向代理或管理隧道，转发至 `127.0.0.1:13020`，并保留管理员登录。管理入口与游戏入口分别配置、分别检查。

## 连接失败时

| 现象 | 优先检查 |
| --- | --- |
| 面板能打开，游戏加入失败 | 游戏是否就绪、客户端版本、Nebula 实际端口、游戏防火墙与转发规则 |
| 本机能加入，局域网另一台设备失败 | 是否误填回环地址、Windows 入站规则、局域网地址是否变化 |
| 局域网能加入，外网失败 | 公网是否可入站、运营商 NAT、路由器转发、云安全组、DNS 与所选转发服务 |
| 能加入，但无人时世界不推进 | 查看 TPS 与无人暂停设置，并核对 [README 的已知限制](../README.md#已知限制) |

需要更完整的部署检查时，参见[项目发布验证与部署检查](acceptance.md)。
