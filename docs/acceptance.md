# 部署与实际验收

本地夹具、演示页面和编译结果用于验证实现。真实服务器验收须使用同一份已校验发布包，记录实际结果；未执行的项目保持“未验证”。验收中的存档、玩家记录、主机路径、网络配置和日志存于私有目录，不提交到公开仓库。

## 部署前

1. 记录发布版本、源码提交、ZIP 与 Bridge DLL 的 SHA-256，运行类型检查、单元与集成测试、Bridge 协议测试和浏览器流程。
2. 核对 Windows 主机、游戏可执行文件、当前受管 PID、启动任务、私有配置和数据目录。存在同根多个游戏实例时先调查，不能随机选择。
3. 由游戏完成一次保存，将 `.dsv`、同名 `.server` 和已有 `.moddsv` 作为一个整体备份，复读文件大小与 SHA-256。保留原 Bridge、配置、任务 XML、面板版本和安装状态。
4. 在隔离目录验证发布包的安装、升级、失败回退和卸载。卸载只移除面板受管任务，游戏和业务数据保留。
5. 使用 `configure-game.ps1 -PrepareOnly` 生成本次游戏接入计划，核对实际变更，再在计划停服窗口应用完整批次。

## 功能验收

| 流程 | 实际通过证据 |
| --- | --- |
| 启动、保存、停止、重启 | 受管 PID 与新鲜签名 Bridge 状态一致；保存回执与完整文件组一致；停止后原 PID 确实退出；重启得到新的就绪进程 |
| 备份与恢复 | 下载备份可复读；恢复前副本存在；恢复后整组散列正确，游戏能加载目标存档 |
| 模组与配置 | 安装、启用、停用、移除和恢复实际改变对应包；依赖冲突在停服前报告；配置预览、历史恢复与密钥保留正确 |
| 更新与版本锁 | 游戏、Nebula、BepInEx 和普通模组显示实际版本；依赖与锁定检查生效；更新后可启动，失败测试能恢复原内容 |
| 更新中断恢复 | 在隔离目录模拟中断；下次操作恢复已验证的原状态；未知文件变更不被覆盖；记录与实际版本一致 |
| 玩家 | 实际加入、离开对应签名事件；踢出仅针对所选会话连接，并等待游戏正常清理；断开后可以重新加入 |
| 客户端包 | 新建隔离的 r2modman 配置，实际导入 `.r2z`、下载锁定版本，并用该配置加入服务器；不能以 ZIP 可解析代替实际导入 |
| 日志和监控 | 页面关闭后仍采样、备份；日志过滤与下载可用；CPU、内存、磁盘、UPS、TPS 和网络的实际采集口径明确，缺失值不当作零 |
| 故障恢复 | 游戏意外退出触发有次数上限的恢复；手动停止不会自动启动；变更失败会暂停自动恢复 |
| 无人值守启动 | 实际重启 Windows，未人工登录时面板任务启动；启用恢复且此前要求运行的游戏回到就绪；确认任务账户可访问全部持久化目录 |

名单和角色权限不属于当前 Nebula 版本提供的接口。不要用存档身份、全局密码或内部远程命令登录集合冒充这些能力，详见 [Bridge](bridge.md)。

## 网络、性能与观察

管理入口和游戏入口分别验收。管理入口需要实际 HTTPS、证书与未登录访问检查；游戏入口需要一个来自外部网络的真实游戏客户端完成加入，并在游戏内看到可运行的世界。网页、TCP 探测和端口监听不能代替实际入服。

性能记录至少注明存档、硬件、游戏与模组版本、玩家数量、目标 UPS、实测 UPS/TPS、CPU、内存和观察时段。先获得固定存档的空载基线，再增加真实玩家与实际工厂负载，记录下降点和恢复情况。以 60 UPS 为目标，不能把启动参数设为 60 当作达到 60 的证据。

持续观察期间记录异常退出、恢复次数、自动备份、磁盘余量和资源增长。最终报告应分别列出已验证流程、未验证流程、实测容量与已知限制，并保留可执行回退步骤。
